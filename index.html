Context Engineering Series · Part 3

Teaching Claude to Connect

Part 1 gave Claude memory, but it still couldn't touch anything outside the conversation. MCP servers give it direct access to your CRM, your code, your docs, and your channels, so you stop being the one who copies things in.

When I wrote this I was running 9 servers with more than 120 tools between them, all on one protocol, plus a case study where the standard integration path didn't exist and we had to build around it.

What Memory Can't Reach

After Part 1, Claude remembers your corrections, your architecture decisions, and your product naming rules. But ask it to pull up the Acme account, or check what's in Slack, or look at that PR, and it can't, because none of that lives in memory.

So you end up doing the fetching for it. Ask what Acme owns and you're the one in Salesforce, clicking across multiple account variants, screenshotting the asset page, pasting it into the conversation and hoping Claude reads the formatting correctly. A PR review goes worse, since you copy the diff, paste it, and lose half of it to context-window limits, and Claude ends up reviewing a fragment without ever seeing the repo. And when you say "send the follow-up to the customer," Claude drafts the email and stops there, leaving you to copy it, open Slack, paste it, fix the formatting, and send it yourself.

Every one of those Alt-Tab round trips burns 30-60 seconds and clutters the context window with raw, unstructured data. Do it 20 times in a session and you've lost 10-20 minutes, with 30% of your context window spent on copy-paste artifacts instead of real work.

MCP in 30 Seconds

Model Context Protocol is an open standard from Anthropic that lets Claude call external tools such as APIs, databases, CLIs, and browsers through one standardized interface. Think of it as USB-C for AI, where a single protocol carries whatever capability sits on the other end of it.

There are three pieces worth keeping straight. The protocol itself is a JSON-RPC standard, so any host, whether Claude Code, Cursor, or Windsurf, speaks the same language to any server. A server is a lightweight wrapper around an API, CLI, or service that runs locally or remotely and exposes the tools Claude can call. And a tool is a single capability like "search Slack," "read a PR," or "query CRM," which Claude decides when to call while you either approve each call or auto-allow it.

One more piece of the setup isn't an MCP server at all. It works through tools like ctx_batch_execute, ctx_search, ctx_execute, and ctx_fetch_and_index.

Case Study

Getting Into Salesforce's Own CRM

Our internal CRM holds pipeline, contacts, contracts, installed products, and consumption data. It's the single source of truth for every deal, and I wanted it inside Claude.

The standard route would have been a direct API integration, and getting that approved for an individual SE project wasn't practical, so the usual credential-based patterns were off the table. Our Cloud Run middleware couldn't query the internal CRM either. There was a hard wall between our production infrastructure and the corporate CRM.

What worked was the Salesforce CLI, because it logs in as me.

The sf CLI and MCP Path

  1. 1. Authenticate the CLI locally. sf org login web --alias corp-crm is a browser-based SSO login that uses your existing corporate credentials, with no app registration needed.
  2. 2. Wrap the CLI in an MCP server. A custom Node.js MCP server calls sf data query --query "SELECT..." --target-org corp-crm under the hood. Claude calls the tool, and the server runs the CLI.
  3. 3. Push results forward into a cache. The middleware still can't reach the CRM on its own, so MCP gathers the data and pushes it to a middleware cache (Redis 4h / Cloud SQL 24h), and every production entry point (LWC, Agentforce, Slack) reads from that cache. When something needs fixing, I fix it in one place and it's available everywhere.

Inside the Meridian Server

Meridian is one custom MCP server that wraps our entire intelligence platform, so Claude can pull account briefs, query the corporate CRM, search grounding data, and run financial analysis from a plain-English request. At the time it had 40 tools, split into three groups.

The 11 CRM tools are the ones the case study made possible. crm_account_detail returns firmographics, owner, and team, crm_asset_lines returns installed products with pricing, crm_opportunity_history gives the full deal history, and crm_consumption_plans carries CCR health data, with contacts, cases, contracts, products, search, and query filling out the rest.

Eight intelligence tools sit on the platform itself. aip_analyze runs the full 25-source analysis, aip_account_brief returns the cached brief, aip_enhance re-analyzes a single section, and aip_search_grounding searches 1,598 RAG chunks, alongside tools for health, deployment, opportunities, and activities.

The remaining 21 are composable v4 tools for outside research, like v4_company_brief for a quick multi-source brief, v4_financials for key financial metrics, v4_news for GDELT news with tone analysis, and v4_techstack for technology detection, plus stock, patents, SEC, GitHub, wiki, and meeting prep.

Slack as a Second Data Plane

Slack was the last server I added, and it mattered more than I expected. With it Claude can search Slack, read channels and threads, send messages, and create canvases, but what it really surfaces is the unstructured human signal that no CRM ever captures.

In practice that means I can find that conversation about a deal strategy from last week without scrolling, and Claude can follow a thread to understand the full discussion before it drafts a response. It posts directly too, meeting follow-ups, deal updates, team announcements, and it can publish long-form content like this very post series as a canvas, formatted and ready to share.

Post-Meeting Follow-Up

me: Send the meeting notes to #acme-deal and DM Sarah the action items
  // Claude calls slack_search_users("Sarah")
  // Claude calls slack_search_channels("acme-deal")
  // Claude calls slack_send_message (channel)
  // Claude calls slack_send_message (DM)
claude: Done, posted the summary to #acme-deal and sent Sarah the 3 action items with dates.

Slack and the CRM on the Same Account

Once I authenticated to corporate Slack I briefly wondered whether I still needed the Meridian CRM tools, since a Slack search for "Acme" turns up a lot on its own.

I kept querying our internal CRM separately, and running one account through both servers shows why, they hand back different kinds of information about it.

What Slack turns up is the conversation around the account, who's working the deal, who the AE is, and who's looped in on the technical side, plus mentions of competing platforms and win/loss context from deal channels, how the customer reacted in meetings and what concerns they raised, and risk signals like executive changes, project delays, and escalations the team flagged. It's unstructured and conversational, and most of it never makes it into a CRM field.

Meridian's CRM tools give me the structured, quantitative side, the system of record. For the same account that's the installed products down to exact SKUs, quantities, per-unit pricing, discount percentages, and contract periods, along with every won, lost, and open opportunity with amounts and close dates. It also catches account variants, since multi-org customers appear as separate CRM accounts (core, Slack, Tableau), and consumption health, meaning CCR utilization, contract values, and renewal timelines.

How the Servers Compose

MCP servers don't need to talk to each other, or even know the others exist. Claude is the part that does the integrating, deciding which servers to call and stitching the results back together.

It works a lot like Unix pipes, where each MCP server is a specialized command (grep, sort, awk) and the LLM plays the pipe operator | that chains them, so the servers compose without being coupled to one another.

One Question Across Both Planes

A real workflow, account name replaced, where Claude makes three tool calls across two MCP servers.
me: Prep me for my Acme meeting tomorrow. What do they own, what's the team saying, and what's in the news?

  // one answer built from three sources, and I never left the terminal

Three Servers to Start With

You don't need 9 servers on day one. Start with the three that pull the most weight for SE work, which takes about 15 minutes to set up, and add the rest as you go.

1

GitHub for Code Access (2 Minutes)

claude mcp add github --scope user -- npx -y @modelcontextprotocol/server-github

PR reviews, issue management, and code search, once you set GITHUB_PERSONAL_ACCESS_TOKEN in the env.

2

Context7 for Current Docs (1 Minute)

claude mcp add context7 --scope user https://mcp.context7.com/mcp

Current library docs for any framework, on a free tier with no API key needed, which fixes the stale-training-data problem for technical work.

3

Slack for Communication (5 Minutes)

claude mcp add slack --scope user -- npx -y @anthropic/slack-mcp

Search, read, and send messages. It needs a Slack bot token carrying the channels:history, chat:write, and search:read scopes, and then you set SLACK_BOT_TOKEN.

+

Building Your Own Server

Once you've seen the pattern you can wrap any API. Our Meridian server is ~400 lines of Node.js, each tool is a function that takes params, calls an API, and returns JSON, and the MCP SDK handles the protocol. If your team has internal APIs, dashboards, or data sources Claude should reach, a custom MCP server is 2-4 hours of work for a developer who's seen it done.
